# 05 — Operations

## Build

```bash
./gradlew :openbank-vop-service:build
./gradlew :openbank-vop-service:test :openbank-vop-service:ktlintCheck :openbank-vop-service:detekt
```

Tests need Docker (Testcontainers Postgres). **Building several services in parallel locally yields a false `QuarkusBindException`** — every service shares management port 8086, so two `@QuarkusTest` boots collide. Build them sequentially; CI gives each service its own job and never sees this.

## Deploy

ArgoCD, `payments` component. Rollout with canary (10% → 30% → 100%, `openbank-money-path-canary` analysis) + dual Services for DNS.

```bash
gh workflow run auto-deploy.yml -f services=vop-service
```

| | |
|---|---|
| Namespace | `payments` |
| Ports | 8149 (app), 8086 (mgmt), 8181 (OPA sidecar) |
| Database | `vop-db` (CNPG, `instances: 2`) — secret `vop-db-app` is **generated by CNPG**, not an ExternalSecret |
| Valkey | `redis.payments.svc:6379` — backs the rate limit |
| OPA bundle | ConfigMap `vop-opa-bundle`, generated by `gen-vop-opa-bundle.sh` |
| `AUTHZ_ENFORCE` | **`true`** from day one — a new service has no legacy caller to break, so none of the shadow "would DENY" exposure that keeps the older rails at `false` (issue #750) |

**After any policy change, re-run the generator and commit both outputs.** `subPath` mounts do **not** hot-reload — the pod-roll annotation is what actually restarts the pods, and the generator stamps it. A stale annotation means pods silently keep serving the old policy.

> **Fleet footgun:** 25 of the 26 `gen-*opa-bundle*.sh` hash `rules.yaml` into their checksum. Any `rules.yaml` edit — including adding a service to `money_path_services` — restamps ~22 services' bundles. Since #1187 the gate discovers generators dynamically and catches this. Run them all, commit the lot, then re-run to confirm a clean tree.

## The rate limit is a security control, not throughput management

This is the thing to understand before touching it.

VoP truthfully answers "does this name hold this IBAN?" to any authenticated caller — that is the regulation's purpose, and a payer must be able to check a payee they do not own. **Authorization therefore cannot bound the oracle. Rate is what separates a payer from an enumerator.** It also caps the 1→2 amplification into account-service and party-service, which are themselves money-path.

- **Valkey-backed, not in-process** — vop-service runs multiple replicas; a local counter would give an attacker `limit × replicas` and reset on every pod roll.
- **Fails CLOSED** — if Valkey is unreachable we cannot prove a caller is under the limit, so we 429. This does **not** contradict VoP failing open: a 429 makes the caller render `no_data` and the payment still flows with a warning.
- **Residual:** the limit is per *principal*. N colluding principals still amplify N-fold; there is no global cap. And the platform has no WAF or edge rate limiting at all ([audit](../../../../docs/audits/2026-07-16-platform-audit.md) §4.3), so this is an application-layer control only — it bounds an authenticated caller, not a volumetric attack.

## SLO

Money-path ⇒ both SLOs are required and gated (`check-slo-registry.py`, issue #669), in `pyrra-slo-money-path.yaml`:

| SLO | Target | Window |
|---|---|---|
| `openbank-vop-availability` | 99.9% non-error spans | 30d |
| `openbank-vop-latency` | 99% faster than 1s | 30d |

**Read the availability SLO correctly.** VoP fails open, so an error here does *not* fail a payment. This SLO measures the health of a **regulatory control** — burning the budget means payers are going **unwarned**, which is the compliance failure, even while the money path itself looks green.

The latency SLO is the tight one: a verify is a two-hop lookup on the payer's critical path. It is the metric most likely to surface the latency cost ADR-0171 accepts as a known negative.

## Runbooks

### `no_data` rate spikes

1. Which reason? `LOOKUP_UNAVAILABLE` ⇒ account-service or party-service is unhealthy — check their SLOs first; VoP is the messenger.
2. `NO_SCHEME_CONNECTIVITY` for **domestic** IBANs ⇒ `VOP_DOMESTIC_IBAN_PREFIXES` is wrong or empty. Real bug.
3. `ACCOUNT_NOT_FOUND` at scale ⇒ either an enumeration attempt (check `requested_by` distribution) or a genuine data problem.

**Payments are still flowing.** VoP fails open; this is a compliance incident (payers unwarned), not a payment outage. Do not "fix" it by holding payments.

### 429s across the board

Almost certainly Valkey, not abuse — the limiter fails closed. Check `redis.payments.svc`. Payers see `no_data` and can still pay; the exposure is that the enumeration control is off while it lasts.

### A `close_match` complaint ("it showed the wrong name")

Expected within the design: `close_match` is *supposed* to return the real name so the payer can correct a near-miss. If it fires too often, `max-edit-distance` is too loose — **tune from outcome metrics, not from one complaint**. Widening it silently turns genuine mismatches into reassuring amber warnings, which is the tampering risk the threat model names.

### Suspected name enumeration

`requested_by` + `verified_at` on `vop_verification` are indexed for exactly this. A principal with a high `no_match` rate is guessing, not paying. There is **no automated detector yet** — an open item in the threat model.
