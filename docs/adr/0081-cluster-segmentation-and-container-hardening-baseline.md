# Cluster segmentation & container hardening baseline

Date: 2026-06-11
Status: Accepted (2026-06-12 — NetworkPolicy baseline implemented: derived
allow-lists generated by `openbank-infra/scripts/gen-network-policies.py`
cover every service namespace. ENFORCEMENT IS LIVE since 2026-06 — the VPC CNI
network-policy agent runs in standard mode (NETWORK_POLICY_ENFORCING_MODE=standard);
the policies are no longer inert. An edge not captured by a derived allow-list or
a hand-maintained policy is dropped — e.g. app-plane Temporal clients had to be
added to `temporal-network-policies.yaml` (ADR-0101 follow-up) once enforcement
was on.)
Delivery-Status: Partial
Author(s): Jiří Raška

## Context

The platform runs ~34 Kubernetes namespaces (one per business domain plus platform/identity/
observability/messaging), deploys every service from the same hardened container image pattern,
and signs images with Cosign (ADR-0029/0030). But three things were never written down as a
baseline, so there is no single source of truth to derive a "what's our posture" view from — and
no honest plan-vs-reality:

1. **Namespace segmentation model** — which namespace holds what, and what the *isolation*
   contract between them is. The split exists; the contract does not.
2. **NetworkPolicy baseline** — the zero-trust ideal is default-deny east-west traffic, but only
   **2 NetworkPolicies are declared in GitOps** (`kind: NetworkPolicy`), so cross-namespace
   traffic is in practice mostly open. This gap is invisible today.
3. **Pod & image hardening baseline** — the Dockerfile (multi-stage `eclipse-temurin:25-*-alpine`,
   non-root `USER openbank`, Quarkus fast-jar) and the Deployment `securityContext` (runAsNonRoot,
   seccomp RuntimeDefault, fsGroup) are consistent by convention, but unstated as a baseline.

ADR-0074/0079 established the house pattern for this: a **plan-vs-reality dossier in the admin
console, derived from real sources, never hand-typed, gaps shown honestly**. This ADR gives the
cluster/container posture that same treatment.

## Decision

Adopt an explicit baseline and surface it as a derived dossier at **`/docs/cluster`** in the
admin-UI (a peer of `/docs/cloud-architecture`, which covers the AWS edge, and `/docs/service-map`,
which covers service dependencies — this one covers what is *inside* the cluster and *inside* the
image).

**Baseline (target posture):**
- **Namespace segmentation** — one namespace per business domain; platform/identity/secrets/
  observability/messaging/CI each isolated. Cross-namespace calls only over explicit in-cluster
  Services; no shared namespaces for unrelated domains.
- **NetworkPolicy** — default-deny ingress per namespace, allow-list only the declared dependency
  edges (the same edges the service-map already knows). Target: every domain namespace has a NP.
- **Pod hardening** — runAsNonRoot, seccompProfile RuntimeDefault, drop ALL capabilities,
  read-only root filesystem where the workload allows, no privilege escalation.
- **Image hardening** — multi-stage build, JRE-only runtime, non-root user, CycloneDX SBOM
  (ADR-0029), Cosign signature verified by kyverno (ADR-0030), eventually at Enforce.

**Dossier (the derived view):**
- A `cluster-topology.json` snapshot, generated at admin-UI build by `generate-cluster-topology.mjs`
  — a pure GitOps + Dockerfile repo-walk (no creds), same provenance pattern as `governance.json`
  and `infra-lifecycle.json`. It derives the namespace set (from the ArgoCD app destinations),
  the NetworkPolicy / ExternalSecret / ClusterPolicy counts (from the manifests), and the image
  anatomy (parsed from a representative Dockerfile + Deployment securityContext).
- The page renders three honest views — namespace map, defense-in-depth layers, container image
  anatomy — each field tagged **Live / Partial / Planned** with an ADR reference. Gaps (e.g. the
  2-of-34 NetworkPolicy coverage, kyverno still Audit not Enforce) are shown, never faked.

## Alternatives considered

- **Hand-drawn architecture diagram.** Rejected — rots immediately and can lie (violates ADR-0074/
  0079). A derived dossier cannot claim a NetworkPolicy that isn't in GitOps.
- **Live-only via the cluster API.** Rejected as the *primary* source — the admin-UI discovery SA
  (ADR-0051) is least-privilege and would need extra RBAC to list NetworkPolicies cluster-wide.
  The build-time GitOps walk is creds-free and is the source of truth for what is *declared*. Live
  enrichment (current counts) is an additive enhancement, not a dependency.

## Consequences

- A single, honest "cluster & container security" view a non-expert can read (analogies: namespaces
  = sealed floors of the bank; the image = a sealed, x-rayed, signed shipping container).
- The NetworkPolicy and pod-security gaps become **measurable and visible**, turning an invisible
  risk into a burndown (this ADR's baseline is the target the dossier measures against).
- New moving parts: one build-time generator, one BFF route, one docs page — all following existing
  patterns (governance/lifecycle generators, docs pages).

## Compliance impact

- **DORA Art. 6–9 (ICT risk), network/segmentation & hardening controls; EBA ICT guidelines:**
  materialises the network-segmentation and host/container-hardening posture as dated, derived
  evidence with explicit gaps — previously tribal knowledge.
