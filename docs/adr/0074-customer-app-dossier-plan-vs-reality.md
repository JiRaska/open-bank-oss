# Customer-app dossier: plan-vs-reality documentation in the admin console

Date: 2026-06-08
Status: Accepted
Author(s): Jiří Raška

## Context

The KMP customer app (ADR-0064) has acquired a corpus of decisions — the
customer edge + Keycloak realm (ADR-0065), SCA decoupled device approval
(ADR-0021), passwordless auth (ADR-0066), feature flags (ADR-0067), the
onboarding journey (ADR-0069), in-app diagnostics (ADR-0070). Each ADR governs
one slice. **No single surface answers the whole question** an auditor, a new
engineer, or a CTO actually asks: *what is this app, how is it built, how is it
integrated — and how far does the reality lag the plan, across governance,
technology and security?*

The gap is real, and it is already misdocumented. The app's README still
advertises "**F0 skeleton**, `useFakeData = true`, no real network" — but the
committed code says otherwise: `AppConfig.useFakeData = false`, the customer
edge is live at `customer.open-bank.tech` (ADR-0065), and screens read real
accounts/transactions. The app is at **F1**. At the same time, real pieces are
genuinely *not* done: the login screen is still a placeholder (real PKCE is a
TODO), TLS pin hashes are empty (`PINNED_SPKI_HASHES = emptySet()`,
ADR-0066-S3), and the Android `SecureCredentialStore` is still an in-memory
placeholder. So the true plan/reality picture is a *mix* of live, partial and
planned — and the one human-written summary that tried to capture it (the
README) has already drifted from the code. **That drift is the core evidence for
this ADR: a hand-transcribed status rots; the status must be derived from the
code that defines it.**

We already solved the same problem for the infrastructure. `/docs/cloud-architecture`
overlays the ADR-0027 target with the **real** state of the sandbox EKS cluster
(`live` / `partial` / `planned`), explicitly to "document the gap honestly
instead of selling the target." The customer app — the half of the platform a
regulator can actually see — has no equivalent. For DORA Art. 8 (ICT
asset/architecture register) and CNB ICT/outsourcing expectations, an honest
as-built of a customer channel is material evidence; an aspirational deck is not.

The binding constraint is non-negotiable #7 (ADR-0029): **catalog & coverage
data are derived, never hand-edited.** ADR-0071 had to retire an 825-line
hand-maintained `manifest.ts` for exactly this reason, and resolved it with a
two-part rule: *declare the curatorial facts that no code expresses, derive
everything else.* The wrinkle here is that the customer app is a **separate
repo** (`openbank-app`), so unlike `catalog.json`/`governance.json` — which are
generated by walking the monorepo — this dossier's "reality" signal has to cross
a repo boundary. The README drift proves we cannot paper over that with a
hand-typed array in the admin-ui.

## Decision

We will add an **application dossier** at `/docs/customer-app` in the admin
console — a living, bilingual (CS/EN) plan-vs-reality view of the customer app —
governed by the following invariants.

**1. Plan-vs-reality is the spine; the honest gap is the point.** Every
capability is rendered as *target* (which ADR governs it) → *real state*
(`live` | `partial` | `planned`) → *the gap*, reusing the **same `live/partial/planned`
vocabulary and `STATUS_META` aesthetic** as `/docs/cloud-architecture`. (Those
status primitives are today inline in the cloud-architecture page, not exported;
extracting them into a shared `docs/_status` module so both pages import one
definition is a tracked follow-up — until then the dossier mirrors the pattern
rather than importing it, and this ADR says so rather than overclaiming.) The
page documents the gap; it does not sell the target. A capability still on a
placeholder renders `partial`/`planned` with the real state stated plainly.

**2. Three lenses: governance, technology, security.** Each capability carries
one or more lenses, so one dossier serves an auditor (governance/security) and
an onboarding engineer (technology) without forking into three documents. The
layout is: *Overview* → *Technology* (how it is built) → *Integration* (how it
is wired to the edge) → *Security* → *Plan-vs-reality matrix* → *ADR index*.

**3. Derive from code; declare only the curatorial; transport as a generated
artefact.** This is the #7-compliant core, drawn honestly:
- **Derived from code** — the facts the README got wrong are extracted from the
  source, never transcribed: `useFakeData`, `EDGE_BASE_URL`, OAuth scopes, cert-
  pinning state from `AppConfig.kt`; app version from `version.txt`. A generator
  (`openbank-app/scripts/generate-app-status.mjs`) reads these. If `useFakeData`
  flips, the dossier flips — it cannot show `true` when the code says `false`.
- **Derived at view time** — ADR existence, title and status resolve against the
  live ADR index (`loadAdrIndex`, the same source `/docs/adr` uses). ADR status
  is never copied into the dossier.
- **Declared (curatorial)** — the facts no code expresses, and which *are*
  genuinely hand-curated: the capability list, the lens tagging, the per-gap
  narrative, and the `decision missing` judgment. These live in
  `openbank-app/app-status.yaml`, **next to the code they describe**, schema-
  validated — the same "declare with the code, then derive" rule ADR-0071 set.
  This ADR does not pretend these are derivable; they are curation, owned by the
  app team and reviewed with the app's PRs.
- **Transport** — the generator emits `app-status.json` (schema
  `openbank.appstatus/v1`) joining the derived + declared layers with an `asOf`
  stamp. Here the cross-repo nature forces a deliberate **difference** from
  `catalog.json` / `governance.json`: those are *git-ignored* and baked at build
  because they derive from the **same** monorepo the admin-ui builds from.
  `app-status.json` derives from a **different** repo that is *not* present at
  admin-ui build time, so the committed artefact **is** the transport — the
  admin-ui Dockerfile `COPY`s it, never reaching across a filesystem to a sibling
  checkout. `openbank-app` CI regenerates it from its own source and publishes it
  back; a generated, byte-stable (no timestamp, repo identifier not a local path)
  committed file. This is a **new integration, not a mirror** of the in-repo
  governance walk; calling it a mirror would be the false analogy that hides the
  hard part.

**4. Every gap points to a decision, or is flagged decision-missing.** A gap
that is a deliberate choice links to its ADR (resolved via `loadAdrIndex`). A gap
the app team judges *should* have a decision but does not is declared
`decisionMissing: true` in `app-status.yaml` and renders a `decision missing`
badge. The dossier thus becomes a governance instrument that surfaces
undecided customer-facing capabilities. The first gap it surfaces —
hardware-backed credential storage (the Android in-memory placeholder) — is being
closed by **ADR-0073**.

**5. CI keeps it honest, advisory → enforce.** CI regenerates `app-status.json`
and **diffs the derived block** against the committed copy — a content check that
would have caught the README drift, far stronger than a date heuristic. Following
the ADR-0071 / ADR-0034 rollout, this starts **advisory** (PR comment / warning)
and flips to **enforce** (fail) once `app-status.yaml` exists and the derived
block is clean. The `asOf` stamp is shown to readers as a freshness hint and
raises an advisory warning past a defined age — it never hard-fails a release on
its own.

**6. Read-only, staff-only, secret-free.** A `docs:view` read surface. It shows
*derived metadata* (build phase, which ADR governs SCA, whether pinning is on) —
never tokens, keys, or SCA payloads (there are none to show; it reads metadata,
not device state). Inherits ADR-0070's redaction posture for anything device-side.

## Alternatives considered

- **A Markdown/MDX page, or a section in the openbank-app README.** Simplest, but
  it cannot carry the derived overlay or live ADR status, targets the wrong
  audience (auditors live in the admin console), and rots silently — the README
  drift documented above *is the demonstration*. Rejected.
- **Hand-authored status array in the admin-ui TSX (asOf-stamped "interim").** The
  first draft of this ADR proposed exactly this as a v1 shortcut. Rejected on
  review: it is `manifest.ts` reincarnated in a different repo from the code it
  describes, and the README proves a hand-transcribed `useFakeData` ships already
  wrong. The derived block (invariant 3) must run from day one; there is no
  hand-typed interim.
- **Fully derived, zero declared.** Infeasible: the capability list, lens tagging
  and gap narratives are curation, not in code — the same wall ADR-0071 hit.
  Resolved the same way: declare the curatorial bit as-code in `app-status.yaml`.
- **Extend `/docs/cloud-architecture` with a customer-app zone instead of a new
  page.** Tempting (it already documents "the other half" and owns the
  primitives), but that page is scoped to the EKS substrate and reads
  `/api/infra/status`; the customer app is a client with a different data source
  (`app-status.json`) and a three-lens framing. We **mirror its status vocabulary**
  (invariant 1) but keep a separate route so neither page's data model bleeds into
  the other. Rejected as a merge; the shared status primitives are a follow-up.
- **Reuse `/docs/service-map` or Docs-as-Service (ADR-0019).** The service map is
  backend-service-shaped (health, lineage); the app is a client, not a deployed
  service with `/q/health`. Docs-as-Service is a per-service pilot. Neither frames
  plan-vs-reality across three lenses. Rejected for now; `app-status.yaml` can
  later fold into Docs-as-Service without changing the dossier's consumers.

## Consequences

**Positive**
- One honest, partly-derived as-built of the customer channel for audit (DORA
  Art. 8), onboarding and architecture review — the same honesty bar the cluster
  already meets, on the half a regulator can see.
- The derived block makes a class of drift (README-vs-code) a CI signal, not a
  thing humans must notice.
- The dossier surfaces *decision-missing* gaps, turning documentation into a
  governance feedback loop.

**Negative**
- A genuinely new cross-repo step: `openbank-app` CI must publish
  `app-status.json` and the admin-ui build must ingest it. This is real work, not
  a config tweak; scoped and owned, not hand-waved.
- `app-status.yaml` is a new per-repo curatorial artefact the app team must keep
  current; mitigated because it sits next to the code and is reviewed with it.

**Neutral**
- Adds one docs route (`/docs/customer-app`), one sections-array entry and one
  sidebar entry — the established way to add a docs folder. Route slug stays
  English (`customer-app`) per the existing convention; the *title* is bilingual
  (“Aplikace” / “Customer App”).
- Reuses the `/docs/cloud-architecture` primitives; no new UI vocabulary.

## Compliance impact

- PCI DSS: not applicable (no cardholder data in the dossier).
- DORA:    Art. 8 (ICT asset/architecture register) — an honest, partly-derived
           as-built of a customer-facing channel; Art. 11 — links the
           diagnostics / correlation path (ADR-0070) into the same surface.
- GDPR:    not applicable directly (metadata only; no personal data, invariant 6).
- PSD2:    documents the SCA (ADR-0021) posture *including the current gap*
           (placeholder credential store, empty pin set), rather than implying
           compliance the app has not reached.
- CNB:     supports ICT documentation / outsourcing expectations with a
           trustworthy as-built of the customer channel.
