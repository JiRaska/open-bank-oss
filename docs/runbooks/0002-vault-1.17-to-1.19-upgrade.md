# Runbook 0002 — HashiCorp Vault 1.17.2 → 1.19.x upgrade

> **SUPERSEDED by [0005 — Vault → OpenBao migration](0005-vault-to-openbao-migration.md).**
> Migrating to the LF-governed, MPL-2.0 OpenBao fork solves the EoL problem without staying on
> HashiCorp's BUSL licence (same reasoning as Redis → Valkey). Kept as the fallback if the
> OpenBao migration is rejected.

Status: Draft (needs a maintenance window)
Owner: Platform / Security
Related: ADR-0079 (infra lifecycle), /approvals proposal "Upgrade Vault 1.17.2 → 1.19.x"

## Why

Vault **1.17.2** is **~609 days past End-of-Life** (EoL 2024-10-09). It is the platform
secrets backend, so running it unsupported is a direct ICT/security-risk finding. Target
the **latest supported 1.19.x** line. **Vault 2.0 is explicitly out of scope** here — it is
a major with licensing/API changes (BSL → the post-1.x model) and must be its own decision
(separate ADR), not folded into a patch-hygiene upgrade.

Deployment (`openbank-infra/gitops/apps/vault.yaml`): Helm chart **`hashicorp/vault@0.28.1`**,
**HA mode with `raft` integrated storage**, `replicas: 1`, dataStorage on `gp3`.

## What 1.18 → 1.19 brings

- Back into security support (fixes accumulated across 1.18/1.19, incl. several CVEs).
- 1.18: improved PKI, plugin/identity enhancements.
- 1.19: secrets-sync GA improvements, audit/perf fixes.
- No storage-format break within the 1.x line (raft snapshots are forward-compatible).

## Upgrade path

Vault supports skipping patch versions but **upgrade one minor at a time** is the
supported, low-surprise path: **1.17 → 1.18 → 1.19**. With the Helm chart this means two
sequential `targetRevision` bumps (the chart `appVersion` tracks the Vault binary; pick the
chart releases whose `appVersion` is 1.18.x then 1.19.x — verify the chart index at upgrade
time).

> Single-replica raft note: `replicas: 1` is effectively a single-node raft. There is **no
> HA headroom** — the upgrade is a brief full outage of Vault while the one pod restarts.
> Schedule a window; expect secrets reads to fail for the restart duration. Apps using the
> Vault Agent / cached secrets ride through a short blip; anything reading Vault live does
> not.

## Pre-checks

- [ ] Confirm the **unseal method**. Auto-unseal (KMS/transit) → the pod unseals itself on
      restart. Manual/Shamir → have the **unseal keys** ready; the pod comes up *sealed*
      and must be unsealed by hand (`vault operator unseal`) or it will not serve.
- [ ] Record current state: `vault status` (version, sealed, HA mode, raft peers).
- [ ] Confirm `gp3` PVC and note its name — it is reused, never deleted.

## Upgrade steps (per minor hop)

1. **Raft snapshot (mandatory backup)**:
   ```
   kubectl exec -n vault vault-0 -- vault operator raft snapshot save /tmp/vault.snap
   kubectl cp vault/vault-0:/tmp/vault.snap ./vault-<date>.snap
   ```
   Store the snapshot off-cluster.
2. **Bump the chart** `targetRevision` in `vault.yaml` to the release whose `appVersion`
   is the next minor (1.18.x first). PR → merge → ArgoCD sync.
3. The StatefulSet rolls the pod. With a single replica it restarts in place.
4. **Unseal** if not auto-unsealed (`vault operator unseal` ×threshold).
5. **Validate**:
   - `vault status` → new version, `Sealed: false`, raft healthy.
   - `GET /v1/sys/health` → 200, `version` is the new minor.
   - Smoke-test a known secret read (e.g. an app's path) and a login via the configured
     auth method.
6. **Repeat** steps 1–5 for the **1.19.x** hop.

## Rollback

If a hop misbehaves: revert the gitops PR to the prior `targetRevision`. If storage was
somehow affected, **restore the raft snapshot**:
```
vault operator raft snapshot restore ./vault-<date>.snap
```
Because we snapshot before each hop, the blast radius is one minor.

## Follow-ups

- Consider raising `ha.replicas` to **3** so future Vault upgrades are zero-downtime
  rolling restarts instead of a full outage (separate change).
- Vault **2.0** evaluation → its own ADR (licensing/API impact).

## Verification (done when)

- `/infrastructure` shows Vault on 1.19.x inside its support window (no longer "past EoL").
- A secret read and an auth login succeed post-upgrade.
