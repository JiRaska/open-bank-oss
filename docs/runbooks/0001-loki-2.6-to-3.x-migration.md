# Runbook 0001 — Loki 2.6.1 → 3.x migration (loki-stack → loki chart)

Status: Draft (needs a maintenance window)
Owner: Platform
Related: ADR-0079 (infra lifecycle), /approvals proposal "Migrace Loki 2.6.1 → 3.x"

## Why

Loki **2.6.1** is **~1308 days past End-of-Life** (EoL 2022-11-10) and **3 majors**
behind (latest 3.7.2). The root cause is the chart: we run the **deprecated
`loki-stack` chart @2.10.2** (`openbank-infra/gitops/apps/loki.yaml`), which is frozen on
the Loki 2.6.x line and no longer maintained. This is therefore a **chart migration**, not
a `targetRevision` bump:

- old: `grafana/loki-stack` (Loki 2.6.x, single binary, **boltdb-shipper** index,
  `table_manager` retention)
- new: `grafana/loki` (Loki 3.x, **TSDB** index, **compactor**-based retention)

Current values (loki.yaml): single binary, `persistence` 10Gi gp3, `promtail` enabled,
`grafana` disabled, retention 72h via `table_manager`.

## What 3.x brings

- Back into security support (3 years of fixes), incl. several CVEs fixed in 2.7–3.x.
- **TSDB** index (default since 2.8): far lower memory, faster queries than boltdb-shipper.
- Structured metadata, native OTLP ingest, query accel / bloom filters (3.x).
- `table_manager` is removed → retention is enforced by the **compactor** instead.

## Key risk

The index format changes (boltdb-shipper → TSDB). Loki supports **multiple `schema_config`
periods**, so the migration is *additive*: keep the old period for already-written chunks
(still queryable) and add a **new TSDB period starting on a future date**. No bulk re-index
of historical logs is required; old data simply ages out under the 72h retention.

Because our retention is only **72h**, the simplest safe path is: cut over the schema with
a `from:` date 24–48h in the future, let the last boltdb data expire, done.

## Pre-checks

- [ ] Confirm retention is acceptable to keep at 72h (compactor config below).
- [ ] Note the PVC (`gp3`, 10Gi) — reused; do **not** delete it.
- [ ] Grafana Loki datasource URL stays `http://loki.observability.svc:3100` (we keep
      `fullnameOverride: loki`, so the Service name is unchanged → no datasource edit).
- [ ] Confirm promtail stays (or plan the Alloy migration separately — out of scope here).

## Migration steps

1. **Snapshot the current state** (audit trail): export the rendered loki-stack manifests
   and the current `schema_config` (Loki 2.6 default = `boltdb-shipper`, period `index_`).
2. **Author the new app** `openbank-infra/gitops/apps/loki.yaml`:
   - `chart: loki`, `repoURL: https://grafana.github.io/helm-charts`, pin
     `targetRevision` to the current `loki` chart (≈6.x → Loki 3.7.x; verify the chart
     index at migration time).
   - `deploymentMode: SingleBinary` (1 replica) to match today's footprint.
   - Reuse the existing PVC via `singleBinary.persistence` (10Gi, gp3).
   - `schema_config` with **two periods**:
     ```yaml
     schemaConfig:
       configs:
         - from: 2022-01-01            # legacy chunks already on disk
           store: boltdb-shipper
           object_store: filesystem
           schema: v12
           index: { prefix: index_, period: 24h }
         - from: <today+2 days>        # cutover → TSDB
           store: tsdb
           object_store: filesystem
           schema: v13
           index: { prefix: tsdb_index_, period: 24h }
     ```
   - Retention via compactor (replaces `table_manager`):
     ```yaml
     limits_config: { retention_period: 72h }
     compactor:
       retention_enabled: true
       delete_request_store: filesystem
     ```
   - `gateway.enabled: false`, `test.enabled: false` for the single-binary footprint;
     keep `grafana.enabled: false`.
3. **Deploy via ArgoCD** (PR → merge → sync). The new `loki` pod starts, reads the old
   boltdb chunks for queries < cutover and writes new chunks via TSDB after the cutover.
4. **Validate**:
   - `GET /ready` and `GET /loki/api/v1/status/buildinfo` → version 3.x.
   - In Grafana, run a query spanning **before and after** the cutover timestamp; both
     return rows.
   - Confirm promtail is shipping (recent log lines appear).
5. **Decommission** the old `loki-stack` release once the new app is Healthy and queries
   pass. ArgoCD replacing the app handles this; verify no orphaned `loki-stack-*` pods/PVCs.

## Rollback

Revert the gitops PR. The old `loki-stack` chart redeploys against the **same PVC**; the
boltdb chunks are intact (we never delete the PVC). Logs written under TSDB during the
window are lost on rollback, but the index period is additive so this is bounded to the
window. Take a `kubectl get pvc -n observability` note before starting.

## Verification (done when)

- `/infrastructure` shows Loki on a 3.x version inside its support window (no longer
  "past EoL").
- Grafana log queries work across the cutover boundary.
