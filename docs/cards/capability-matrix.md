# Card scheme capability matrix

What each card network offers, which port this platform models it behind, and what this
repository actually implements today. Generated from the capability registry; edit the
registry, never this file.

**`bindings` is the honest column.** It records what is implemented here, not what is
possible. A capability whose only binding is `simulator` has no vendor integration, and
saying so is the point — a matrix that reads like an integration status page cannot be
told apart from a plan.

**`availability` is about the SANDBOX**, not a production contract: `sandbox` means an
adapter can be exercised for free from the developer portal, `contract required` means no
call succeeds before a commercial agreement is signed.

## Why each capability is here

- **BIN and card-product attributes** — Answers what a card number's issuer range is: brand, product type, country, funding source. First because it is read-only, needs no cardholder data, and is the missing WRITER for the merchant/BIN reference data the transaction categoriser is starved of (#8573).
- **Merchant identification and location** — Turns an acquirer's merchant descriptor into a named, located merchant. Drives the customer's "where was this" and the categorisation the card controls act on.
- **Network tokenisation (wallets, card-on-file)** — A network token replaces the PAN at the merchant, so a breach at one merchant cannot be replayed. Also the mechanism behind wallet provisioning.
- **Push payment to a card** — Sends funds TO a card rather than pulling from one — disbursements, refunds outside the original authorisation, person-to-person.
- **Disputes and chargebacks** — The scheme's own case lifecycle, reason codes and evidence exchange. The bank-side lifecycle is ADR-0117; this is the wire to the network.
- **Card-on-file account updater** — Tells merchants holding a card on file that it was reissued, so a subscription does not fail on a card the customer has replaced.
- **Network-side spend controls** — Controls evaluated by the network before the authorisation reaches the issuer. Deliberately portless for now: this platform enforces its controls at card-issuance (ADR-0194), and duplicating them at the network would create two copies of one control — the exact drift the card platform is designed to avoid. Registered so the choice is visible rather than missing.
- **3-D Secure / issuer authentication** — Out of scope by ADR-0283 D2 and ADR-0190 before it: an issuer Access Control Server needs EMV 3DS certification and a real cardholder-authentication relationship. Registered here so the absence is a recorded position rather than an omission a reader has to infer.
- **Scheme FX rates** — The rate a scheme applies to a cross-currency card transaction. Portless because fx-service already owns rate sourcing (ADR-0171 sibling); a second source would have to be reconciled with it, and that is a decision, not an adapter.

## Authenticating to each network's sandbox

- **Visa** (https://developer.visa.com): mutual-TLS + API key (MLE on some products).
- **Mastercard** (https://developer.mastercard.com): OAuth 1.0a request signing.

Credentials live in OpenBao and are read only by the adapter module that needs them; no service outside an adapter sees a network credential.
