# Threat model - openbank-finrep-service

## Scope

FINREP preview and return assembly (F01.01, F01.02, F01.03, F02.00 and others) from the ledger trial balance. It posts nothing; the asset is the correctness of a regulatory figure.

## Accepted limitations (#13189)

- **Shared accrual accounts.** GL 1520/1521 (accrued interest receivable) and 2310/2311 (accrued interest payable) are shared between ČNB and interbank counterparties. The mapper cannot split them, so ČNB accrued interest receivable is reported with loans and advances (F01.01 r0181/r0183) and accrued interest payable is reported under credit institutions (F01.02 r0150) rather than partly under central banks (r0130). Impact: misclassification between sub-lines of the same parent, totals unaffected. Resolution: separate ledger accounts per counterparty class, carried by the product revision `regulatoryClass` (ADR-0341).
- **Nostro overdraft granularity.** Overdraft is detected per ledger line of GL 1001/1002 (account and currency), not per correspondent bank, so two nostros of one bank in different currencies are not netted before the check.
- **Unverified datapoint ids.** F01.01 r0030 and F01.02 r0130/r0150 are emitted with the row coordinate from the EBA template but without a datapoint id verified against the pinned annotated templates (fixture entries carry null). XBRL-CSV preflight blocks any return containing them (`UNVERIFIED_DATAPOINT_ID`), so they cannot be silently submission-ready. Tracked in #13603.

## Submission lifecycle

finrep now persists one submission per (template, reference period, revision) in its own Postgres (`finrep-db`), with every transport attempt and the supervisor's acknowledgement. Threats and controls:

- **A dry run read as a filing (repudiation / integrity).** No live supervisory transport exists in this repository. The default `SupervisoryReturnTransport` answers `DRY_RUN`, a value of its own that never advances the return past PACKAGED and is never shared with `SUBMITTED`. `ACKNOWLEDGED` is reachable only from `SUBMITTED`, so a dry run cannot be acknowledged into an apparent filing.
- **Packaging an ineligible return.** Packaging re-runs the XBRL-CSV preflight and refuses with 409 while any blocker is present. The stored package is a hashed manifest (identity plus framework and taxonomy versions), not a rendered XBRL-CSV archive.
- **Duplicate filing of one revision.** The unique key on (template_id, reference_period, revision) makes open idempotent. A concurrent open that loses the INSERT race returns the winning row (200), not a 500. A re-submit of a return already SUBMITTED, ACKNOWLEDGED or REJECTED returns it without another transport call.
- **Concurrent submits (double filing).** Before the transport is called, the submission is claimed with a conditional `UPDATE … SET state='SUBMITTING', claimed_at=now WHERE id=? AND state='PACKAGED'`. A caller that updates 0 rows does not transmit: it gets 409 `SUBMISSION_IN_PROGRESS`, or the settled return. The final transition is itself conditional and FENCED on the claim token (`… WHERE state='SUBMITTING' AND claim_id=<this holder's claim>`), and the attempt row is written in the same transaction only when that update moved exactly one row. `SupervisorySubmissionConcurrencyIT` drives two parallel submits and asserts exactly one transport call; it fails (2 calls) with the claim disabled.
- **A claim left behind (stuck or wrongly retried return).** Once claimed, every exit records an outcome with an attempt row, and the recording runs `NonCancellable`. A transport that throws, or a request cancelled mid-call, is recorded as `UNKNOWN` (state `OUTCOME_UNKNOWN`), because it may have delivered. Only an adapter that returns `FAILED`, meaning it is certain nothing was sent, releases the return to PACKAGED. OUTCOME_UNKNOWN is never resubmitted automatically: submit answers 409 until an ADMIN calls `POST …/reconcile` (sent with the supervisor's reference, or not sent). If the store itself fails while recording, the claim stays SUBMITTING until `claimed_at` passes the lease (`openbank.finrep.submission.claim-lease`, default 15 min, which must exceed the transport timeout). It then lapses to OUTCOME_UNKNOWN with a `claim-lease` attempt, again never back to PACKAGED. Covered by `SupervisorySubmissionRecoveryIT` (throwing transport, lapsed lease, fresh lease, ADMIN-only reconcile).
- **A lapsed holder overwriting a newer claimant.** Every claim gets a fresh `claim_id`, and every holder transition (outcome, the OUTCOME_UNKNOWN late-answer fallback, lapse, reconcile) is conditional on it. A holder whose claim lapsed, was reconciled and was re-claimed by someone else moves 0 rows. Its late result is not applied and is recorded only as an `UNKNOWN` attempt under its own claim id, with the real result in `detail`, so an operator can see a possible second delivery. `SupervisorySubmissionFencingIT` drives that exact interleaving: A stuck, lapse, reconcile, B files, A answers late.
- **Concurrent acknowledgements (silently overwritten verdict).** Recording an acknowledgement is a conditional `UPDATE … WHERE id=? AND state='SUBMITTED'`, with a `supervisor-acknowledgement` attempt row (reference, verdict, actor) written in the same transaction only when exactly one row moved. Two concurrent acknowledgements that both read SUBMITTED settle it once: the loser moves 0 rows, records nothing and gets 409, so an accepted verdict can never be replaced by a later rejected one (or the reverse) without trace. `SupervisorySubmissionConcurrencyIT` drives two parallel acknowledgements and asserts 200 + 409 with one evidence row; it fails (200 + 200) with the condition removed.
- **Lost attempt evidence.** Attempt numbers are assigned by the store, inside the writing transaction, as `coalesce(max(attempt_no), 0) + 1` under a `FOR UPDATE` lock on the submission row, never from a count read beforehand. Concurrent writers (a late result, a lapse, a reconcile, an acknowledgement) therefore cannot collide on `uq_finrep_submission_attempt_no` and drop a row. Covered by a parallel-append case in the same IT, which fails with a duplicate-key violation under the old pre-counted numbering.
- **Unauthorised state change.** All routes require ROLE_ADMIN or ROLE_OPERATOR (JWT roles, as for the rest of finrep), and reconcile requires ROLE_ADMIN; the acting principal is recorded on every attempt and acknowledgement.
- **Accepted limitation.** The acknowledgement is recorded by an operator, not received from the supervisor's channel, so its authenticity rests on that operator. Replacing the dry-run adapter with a live one needs institution-held credentials and its own threat-model update.
